## Опис бізнес-логіки предметної області

Система підтримує ролі: адміністратор, HR-менеджер, керівник, працівник.

1. Адміністратор керує користувачами та правами доступу.
2. HR-менеджер веде картки працівників, фіксує кадрові зміни, формує звіти.
3. Керівник переглядає дані команди та погоджує запити (наприклад, відпустки).
4. Працівник переглядає власний профіль і подає заявки.

Операції в системі логуються (дата, виконавець, тип зміни), що забезпечує контроль та аудит змін.

## Функціональні вимоги

1. Автентифікація та авторизація користувачів за ролями.
2. Перегляд списку працівників із фільтрацією (ПІБ, відділ, посада, статус).
3. Додавання нового працівника.
4. Редагування даних працівника.
5. Видалення або архівація працівника.
6. Призначення працівника до відділу та посади.
7. Перегляд історії кадрових змін.
8. Формування базових звітів за відділами та періодами.
9. REST API для операцій GET, POST, PUT, DELETE.

1. Адаптивність інтерфейсу для desktop, tablet, mobile.

## Use-case діаграма та опис

### Актори

1. Адміністратор
2. HR-менеджер
3. Керівник
4. Працівник

### Основні сценарії використання

1. Увійти в систему.
2. Переглянути список працівників.
3. Додати працівника.
4. Оновити дані працівника.
5. Видалити/архівувати працівника.
6. Переглянути історію кадрових змін.
7. Сформувати звіт.

### Текстова Use-case схема

```text
Працівник -> (Перегляд власного профілю)
Працівник -> (Подання заявки)

Керівник -> (Перегляд команди)
Керівник -> (Погодження заявки)

HR-менеджер -> (Додавання працівника)
HR-менеджер -> (Редагування працівника)
HR-менеджер -> (Формування звіту)

Адміністратор -> (Керування ролями)
Адміністратор -> (Керування користувачами)
```

## ER-діаграма та опис даних

### Основні сутності

1. Employee (id, full_name, email, phone, hire_date, status, department_id, position_id)
2. Department (id, name)
3. Position (id, name, grade)
4. User (id, login, password_hash, role, employee_id)
5. LeaveRequest (id, employee_id, start_date, end_date, status, approved_by)
6. AuditLog (id, user_id, action, entity, entity_id, created_at)

### Ключові зв'язки

1. Department 1:N Employee
2. Position 1:N Employee
3. Employee 1:1 User
4. Employee 1:N LeaveRequest
5. User 1:N AuditLog

### Текстова ER-схема

```text
Department (1) ---- (N) Employee (1) ---- (1) User
Position   (1) ---- (N) Employee
Employee   (1) ---- (N) LeaveRequest
User       (1) ---- (N) AuditLog
```

## Хід виконання

### Крок 1. Запуск шаблону

```bash
pnpm i
pnpm svelte-kit sync
pnpm dev --open
```

### Крок 2. Запуск REST API

```bash
npm install
node server.js
```

### Крок 3. Приклад базового маршруту

```js
app.get("/employees", (req, res) => {
  res.json(employees);
});
```

### Крок 4. Виконання практичних завдань REST API

1. Створено Node.js проєкт та підключено Express.
2. Реалізовано HTTP-сервер з відповіддю `Hello from Node.js server`.
3. Реалізовано `GET /students` для отримання JSON-списку студентів.
4. Реалізовано `POST /students` для додавання студента (`id`, `name`, `group`).
5. Реалізовано `PUT /students/:id` та `DELETE /students/:id` для оновлення і видалення.

```http
GET /students
POST /students
PUT /students/:id
DELETE /students/:id
```
